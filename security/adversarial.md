# Adversarial input table — expected vs observed

Every case below is an executable test. Vitest cases live in
`tests/adversarial/adversarial.test.ts`; the engine-level contract is also
covered per-rule in `rules/*/test_rule.test.ts`. Observed statuses were
produced by the recorded run in `evidence/vitest-run.txt` on 2026-11-11.

Statuses: **FLAGGED** (finding raised for human review) · **SAMPLED**
(bounded work, explicitly marked) · **SAFELY_REJECTED** (`SafeRejection`
with a specific code; no partial results) · **PASS-THROUGH** (treated as
inert data; audit completes).

## Residual risks (documented, not hidden)

- The 20 MB in-browser upload cap and the 10M-row hard cap are enforced in
  code (`engine/intake.ts`, `engine/guards.ts`), but memory above ~500k rows
  exceeds free-tier containers; the measured ceiling and the polars server
  path are recorded in `benchmarks/RESULTS.md` and ADR-04.
- Zip-bomb defense checks the workbook's DECLARED dimensions before decoding
  cells. A workbook that lies within declared bounds but still expands
  aggressively cell-by-cell is bounded by the 20 MB upload cap instead —
  defense in depth, not a guarantee.
- Prompt-injection detection is a pattern report, not a sandbox: the engine
  has no execution environment at all (no eval, no model calls in the audit
  path), which is the actual defense. The finding exists so humans see the
  hostile content.
